## 1. The distinct approaches found in the sources

### A. Design-token constraint systems (bound what the agent may emit)

- **What it is.** Encode color, dimension, typography, shadow, etc. as *named, typed, referenced* values instead of ad-hoc literals, and make every styled surface consume the names. The DTCG spec defines tokens as name/`$value` pairs with optional `$type`, `$description`, groups, aliases ("a design token's value can be a reference to another token"), composite types (typography, border, shadow, transition), and a JSON interchange format consumable by "translation tools" (it names Style Dictionary and Terrazzo) that "convert source design token data into platform-specific source code" **[spec]**. Refactoring UI is the practitioner counterpart: "Limit your choices," "Establish a spacing and sizing system," "Establish a type scale," "Define your shades up front" are chapters of its book **[canon]**.
- **Evidence it improves AI-produced UI.** None of the fetched sources *measures* tokens improving agent output — that specific link is **[inference]**. What exists: (1) the spec's own rationale — tokens are "a methodology for expressing design decisions in a platform-agnostic way… establish a common vocabulary" **[spec]**, which matches the project's prior decomposition that agents compose "decently when constrained to tokens and component vocabularies"; (2) this repo's own gate proves the mechanism is enforceable mechanically (a `disallowed-methods` warning means a styling rule was broken, not a false positive — AGENTS.md) **[repo]**.
- **Cost/machinery.** Minimal: a token file + naming discipline + a lint gate. The repo already has all three except geometry, which is exempt by policy and expected to use named constants **[repo]**. Full DTCG adoption is *not* advisable: the fetched TR page is explicitly a preview draft marked "do not implement this version," and the repo's `aurora.json` + gpui-component theme already fills the role **[repo + spec-status]**.

### B. Screenshot-in-the-loop visual critique (give the agent eyes)

- **What it is.** Capture the rendered output, feed the image (plus a critique prompt) to a multimodal model, and iterate on the code until the critique passes. Design2Code is the primary research anchor for the mechanism: it "manually curate[s] 484 diverse real-world webpages as test cases and develop[s] a set of automatic evaluation metrics to assess how well current multimodal LLMs can generate the code implementations that directly render into the given reference webpages, given the screenshots as input," complemented by "comprehensive human evaluations to validate the performance ranking" **[measured]**. Two caveats the same abstract states: models "mostly lag in recalling visual elements from the input webpages and generating correct layout designs" — i.e., the vision→code pathway is real but layout-weak; and the benchmark is single-shot webpage replication, *not* an iterate-until-pass agent loop — any claim that iteration improves quality is **[inference]** not in the abstract.
- **Cost/machinery.** Moderate: capture plumbing (the repo has it on Linux via grim; macOS capture is the open follow-up **[repo]**) + a multimodal model call + a written critique rubric (see C). No server infrastructure needed; cost scales with iterations.

### C. Rubric / heuristic-based design critique (make "not good at all" actionable)

- **What it is.** Convert diffuse taste verdicts into a fixed checklist the agent applies to its own work. NN/g supplies the canonical usability rubric: ten heuristics explicitly framed as "broad rules of thumb and not specific usability guidelines," with the note that they were "refined… based on a factor analysis of 249 usability problems" and "have remained relevant and unchanged since 1994" **[canon]**. Several map directly onto bridge-verifiable artifacts **[inference for the mapping]**: #1 Visibility of System Status, #4 Consistency and Standards ("follow platform and industry conventions" — native-desktop conventions specifically), #6 Recognition Rather Than Recall (labels visible/retrievable), #7 Flexibility and Efficiency (accelerators → the tab-stop map), #8 Aesthetic and Minimalist Design ("interfaces should not contain information that is irrelevant"). Refactoring UI supplies the *visual* half as concrete tactics rather than principles — its pitch page demonstrates the genre with "use fewer borders… try adding a box shadow, using contrasting background colors, or simply adding more space" — and its TOC covers hierarchy ("Hierarchy is Everything", "De-emphasize to emphasize"), spacing ("Start with too much white space", "Avoid ambiguous spacing"), depth ("Use shadows to convey elevation"), and color ("Ditch hex for HSL", "Don't rely on color alone") **[canon]**. Crucially, its premise is that these are learnable "tactics, not talent" — exactly the shape an agent-consumable rubric needs; but the claim that the book makes engineers design better is supported only by testimonials **[anecdotal]**.
- **Evidence.** Heuristic evaluation as a *human* method has a research pedigree (Molich & Nielsen 1990; Nielsen 1994, cited on the page); no fetched source measures an LLM applying these heuristics — that use is **[inference]**.
- **Cost/machinery.** Lowest: one committed rubric document + a review step. No new tooling.

### D. Automated objective UI checkers (lint for the interface)

- **What it is.** Deterministic rule evaluation over UI state — the axe-core precedent. Fetched facts: it is "an accessibility testing engine… built to seamlessly integrate with any existing test environment so you can automate accessibility testing alongside your regular functional testing"; rules exist "for WCAG 2.0, 2.1, 2.2 on level A, AA and AAA as well as a number of best practices"; it "returns zero false positives (bugs notwithstanding)"; results can be "incomplete… where axe-core could not be certain, and manual review is needed"; the README recommends a linter to "catch bugs earlier in the development cycle" **[vendor, but concretely falsifiable in its rule list]**. Its stated detection rate — "on average 57% of WCAG issues automatically" — is a first-party figure **[vendor]**. Contrast checking is a member of this family: a computable function of two colors; axe-core ships a `color-contrast` rule and uses colorjs.io for color-format conversion **[fetched README]**. The exact contrast thresholds were intended to come from WebAIM, whose page 404'd — **not verified here**; treat specific numbers (commonly cited WCAG ratios) as unconfirmed until re-sourced.
- **Evidence it improves AI-produced UI.** No fetched source measures this for agents; the case is that it converts a quality dimension into a pass/fail gate the same way unit tests gate logic — **[inference]**, consistent with axe's philosophy section (automated testing "doesn't require special expertise" and integrates with tests teams already run).
- **Cost/machinery.** axe-core itself is web/HTML-scoped and not directly applicable to gpui. The *pattern* is portable **[inference]**: rules over a structured UI description. The bridge's `tree --json` is precisely such a description (roles, labels, bounds, focus) **[repo]**, so a rule engine here is a pure-Rust module over existing output.

### E. Golden-image / visual regression testing (gate the pixels)

- **What it is.** Screenshot a known-good state, commit the baseline, fail on pixel divergence. Playwright documents the full pattern: `toHaveScreenshot()` generates reference screenshots on first execution ("A snapshot doesn't exist… writing actual"), subsequent runs compare against the reference using the pixelmatch library with a configurable `maxDiffPixels` tolerance; baselines live next to tests, should be committed to version control, and — the key discipline — "review any changes to it"; intentional changes go through `--update-snapshots`; determinism is managed with a custom stylesheet (`stylePath`) to hide volatile elements, and Playwright itself "took a bunch of screenshots until two consecutive screenshots matched" before saving a baseline. The docs also carry the central physics warning: "Browser rendering can vary based on the host OS, version, settings, hardware, power source… For consistent screenshots, run tests in the same environment where the baseline screenshots were generated," which is why snapshot names embed platform (e.g. `chromium-darwin`) **[tool docs]**.
- **Evidence it improves AI-produced UI.** Not measured in fetched sources; its function here is regression *prevention* (keeping a once-approved look from silently degrading), not initial quality — **[inference]**. (Chromatic would have been the "at scale, PR-gated" reference, but its declared page 404'd and nothing from it is used here.)
- **Cost/machinery.** Small: capture (exists), a pixel-diff comparator (the mechanism is library-independent; Playwright's choice is pixelmatch, a JS library — no specific Rust crate is claimed here **[inference]**), committed baselines, an update flag, and a deterministic harness. The repo is unusually well positioned: `--size WxH` fixed windows, `wait-frame` (stronger than Playwright's two-consecutive-shots heuristic, since gpui's frame counter advances only on change **[repo]**), pinned fonts in CI (`fonts-ibm-plex` for "font parity") **[repo]**.

### F. Reference-anchored generation (taste by example, not by words)

- **What it is.** Instead of an open-ended "make it look good," anchor generation to concrete exemplars. Two complementary forms in the sources: (1) *screenshot-as-spec* — Design2Code's whole task is models producing code that "directly render[s] into the given reference webpages, given the screenshots as input" **[measured]**; (2) *exemplar libraries* — Refactoring UI ships "200+ individual component styles" in a component gallery, "over a dozen comprehensive color palettes" with 10 shades per color, and 30+ font recommendations shown in context **[canon; commercial product, $99–149]**.
- **Evidence.** The measured part is that frontier MLLMs (the abstract names GPT-4o, GPT-4V, Gemini, Claude) *can* approximately reproduce a reference screenshot in code, with the known weakness in element recall and layout **[measured]**. For a non-designer owner, "pick the reference you like" is a way to transfer taste without vocabulary — **[inference]**, directly responsive to the owner's stated inability to articulate visual fixes.
- **Cost/machinery.** Low: a handful of committed reference images (or gallery pages) the owner approves once; no SaaS. Caveat: Refactoring UI's examples are web-styled, and the project's prior decomposition already flags web-centric aesthetics as a bias — references should be curated native-desktop examples **[inference]**.

### G. Generator/critic loops with gated review (close the loop in the PR)

- **What it is.** Wire the above into the PR pipeline so *no UI change merges without produced evidence*: agent generates → objective checkers run → goldens compared → vision critique against a rubric → owner reviews rendered artifacts. Pieces of this are literal in the sources: Playwright's "commit [snapshots] to your version control… and review any changes to it"; axe-core's "insert calls at each point in your tests where a new piece of UI becomes visible" and integration with tests you already run; Design2Code's pairing of automatic metrics with human evaluation "to validate the performance ranking" — i.e., the measured benchmark itself treats machine metrics + human eyes as complementary layers **[tool docs / measured]**. The repo already has the social skeleton: PR bodies "carry a human-check list," UI changes must be "exercis[ed]… through the debug bridge first," and docs/0055 specifies PR receipts as "snapshot diffs + screenshots" **[repo]**.
- **Evidence.** No fetched source measures an end-to-end generator/critic loop for agents — **[inference]** assembled from the layers above.
- **Cost/machinery.** Process cost only, plus one CI job; everything needed (sessions, receipts, PR-body artifacts) exists **[repo]**.

## 2. Which combinations are reported to work best together

Combinations that a source itself reports (vs. my synthesis) are separated:

**Reported in-source:**
- **Automatic metrics + human evaluation as complementary layers** — Design2Code explicitly complements its automatic metrics with human evaluations to validate rankings **[measured]**. Translation: objective checks and the owner's eyes are not substitutes.
- **Committed baselines + change review + update discipline + environment determinism** — Playwright's pattern is only sound as a package; it explicitly warns that rendering varies by OS/hardware/power, so baselines must be generated in the same environment that compares against them, and baseline changes must be reviewed like code **[tool docs]**.
- **Constraint layers stacked early→late** — axe-core layers a linter (earliest) → rules inside functional tests (CI) → "incomplete" results routed to manual review **[vendor]**; Refactoring UI's own sequence starts with limiting choices before any layout work **[canon]**.
- **Tokenization + mechanical enforcement** — the repo's existing combination: semantic token vocabulary (docs/0002, `aurora.json`) + a hard lint gate in CI **[repo]**.

**Synthesis — how the pieces compose for this project [inference]:** the layers are complementary because they catch disjoint failure classes: (A) tokens bound what code can express at write time; (C) a rubric converts vague verdicts into named, checkable findings; (D) objective checkers catch structural facts (missing roles/labels, rhythm violations, traps) deterministically; (E) goldens catch *regressions* but say nothing the first time a surface exists; (B/F) vision critique + references address first-pass quality — precisely the "not good at all" case — but are the weakest at layout, which is what (D/E) measure mechanically. Design2Code's measured weakness (element recall, layout) is the argument for never trusting the vision layer alone.

## 3. Shortlist: what this tiny Rust+gpui project can adopt cheaply

Ordered by leverage-per-effort, all building on the existing bridge.

1. **Screenshot critique ritual on every UI PR (hours).** Already 90% built: `session start --size 1280x800` → drive → `screenshot` → PNG into the PR body **[repo]**. Add one step: the agent runs a multimodal critique of the PNG against the written rubric (below) and fixes named findings before requesting review. Evidence basis: screenshots are proven model input **[measured]**; the iterate-until-pass wrapper is **[inference]**. Cost: a model call per iteration. This converts the owner from "verdict after merge review" to "final approver."

2. **A committed critique rubric (a day).** `docs/design-review-rubric.md`: NN/g's ten heuristics restated as per-surface checkable items (several already machine-checkable from the bridge — status feedback visible in the tree dump, labels present for recognition-not-recall, tab order sane via `--tab-stops`, consistent exit paths) plus a Refactoring UI tactics checklist (borders minimized via shadow/background separation, hierarchy explicit, white space generous, spacing on scale, color not sole signal). Every UI PR's critique output cites rubric items. Anchors: **[canon]**; agent-application is **[inference]**. This is the direct cure for "owner cannot articulate visual fixes" — the rubric supplies the vocabulary, the owner only confirms/refutes findings.

3. **`dashboard-debug audit`: axe-style objective rules over `tree --json` (a few days).** Pure Rust over existing output; suggested starter rules: every focusable node has a role+label (AGENTS.md already mandates `.id()` + role and treats a missing node as an element bug); no zero/negative-sized bounds; sibling gap values ∈ the spacing scale (runtime complement to the compile-time lint, closing the deliberately-exempt geometry gap at least in review); no overlapping bounds; tab-stop traps (the walk already detects stuck focus); duplicate labels. Model on axe's design virtues: deterministic, zero-false-positive bias, "incomplete" category for anything uncertain rather than a hard fail **[vendor pattern; rule set is my inference]**. Wire into the `run` receipt scripts so one command produces the audit receipt **[repo integration]**.

4. **Contrast gate over `aurora.json` (half a day).** The theme is already data (`include_str!`-ed JSON with semantic fg/bg slot pairs — `accent.background`/`accent.foreground`, `list.head.background`, `muted.*`, …). A unit test computes the contrast ratio for each declared pair and fails below threshold. Threshold values were to be grounded in WebAIM, which 404'd — pick configurable thresholds and re-source the numbers before hard-coding them **[unverified]**; the *mechanism* (contrast as a computable gate over token values) is established by axe-core's `color-contrast` rule **[fetched]**.

5. **Golden screenshots in CI, Linux-only (2–3 days).** Implement the Playwright pattern natively: baseline dir committed; first run writes golden; CI job (`session start --size` fixed, `wait-frame`, `screenshot`, pixel-diff with a small max-diff tolerance) fails on divergence; `--update-baselines` flag for intentional changes; PR includes the diff when baselines change. Determinism assets already in place: fixed window size, frame-accurate waiting, pinned fonts in CI, sway+grim pinned via nixpkgs **[repo]**. Follow Playwright's environment warning strictly: baselines live and die on the ubuntu-24.04 runner; never compare macOS captures against them — which is also why item 7 exists.

6. **Reference-anchored generation (owner: one hour of choosing).** Keep 3–6 owner-approved exemplar screenshots (native desktop dashboards) in-repo as the visual target; the agent composes gpui-component widgets + Aurora tokens toward the reference instead of toward "good." Measured basis: screenshot→code is a benchmarked, frontier-model-capable task **[measured]**; expect layout drift (the measured weak spot) to be caught by items 3/5, not by the model. Optional Refactoring UI purchase (~$99) supplies exemplar galleries/palettes, with the web-aesthetic caveat **[canon/anecdotal]**.

7. **Close the macOS eyes (the known follow-up).** Until in-app frame capture lands (docs/0010 lists it; macOS receipts are degraded under #401 **[repo]**), the vision loop only runs where CI runs. Prioritize this follow-up so the owner's actual platform is the one being critiqued — otherwise every gate optimizes a rendering the owner never sees **[inference]**.

8. **Deliberately skip.** Full DTCG implementation (spec is a self-declared preview draft: "do not implement" **[spec]**); Chromatic-style SaaS (declared page unverified 404; budget constraint; the PR-gating it represents is reproducible locally per item 5); expecting rubric+vision alone to fix layout precision (measured weakness — keep the mechanical layers).

**Bottom line:** the project's constraint system (tokens + lint gate) is already ahead of what most teams have **[repo]**; the missing systematic layers are exactly the ones its own bridge nearly provides — objective rules over the tree dump, a contrast gate over the theme file, committed goldens in Linux CI, and a written rubric driving a screenshot-in-the-loop critique, with reference images encoding the owner's taste.
